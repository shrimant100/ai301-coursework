# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| `environment-sufficient` | Repro report environment block plus issue/thread version context (see evidence guide: Environment) | Pass if the repro names **OS** and the **primary runtime/tool versions** needed to rerun (e.g. app version, Python, Docker image tag, or repo commit SHA). Fail if OS or all version/commit identifiers are missing. Fail also when the issue or thread **confirms the bug on latest/main/current release** (or the repo template requires latest verification) and the repro uses a **materially older** primary tool version (clear major/minor gap vs latest release in repo facts or vs versions named in the issue/thread) **without acknowledging that skew** while still claiming the filed bug on the current line is confirmed. | required |
| `steps-copy-pasteable` | Repro report steps / execution section (see evidence guide: Steps) | Pass if the repro includes at least **one literal shell command, HTTP call, or numbered UI action** that reaches the bug trigger without unstated magic setup. Fail if steps are only vague ("set up the project", "run the app") with no concrete trigger action. | required |
| `repro-has-artifacts` | Repro report quoted outputs (see evidence guide: Behavior shown) | Pass if the repro quotes at least **one observable result**: command stdout/stderr, HTTP status+body excerpt, log line, or traceback. Fail if the report only narrates success/failure with no quoted output. | required |
| `trigger-faithful` | Issue trigger description vs repro preparation/execution (see evidence guide: Behavior shown) | Pass if the repro uses the **same trigger** as the issue: same input file contents, same endpoint and method, same command flags, or same user sequence the issue describes. Fail if the repro changes the failing construct (e.g. different syntax, different route, different dataset) such that a pass/fail could be an adjacent bug. | required |
| `symptom-matches-issue` | Issue stated actual behavior vs repro quoted artifact (see evidence guide: Behavior shown) | Pass if the quoted actual shows the **same failure mode** the issue describes (same error type/message, same panic signature, same visible UI behavior). Fail if actual is a different class of failure (parse error vs panic, 404 vs 500 with different root cause) while claiming the same bug. | required |
| `expected-and-actual-paired` | Repro report expected/actual sections or inline statements (see evidence guide: Honesty) | Pass if **expected** and **actual** are both stated for the repro attempt, OR the report is an honest **cannot-reproduce** that lists what was tried and what happened instead. Fail if expected is missing, or actual is missing while the report claims confirmation. | required |
| `claim-honest-intent` | Candidate claim comment (see evidence guide: Comms) | **Claim-only draft:** pass if the claim names the **specific issue behavior** and intent to investigate/reproduce (may promise a follow-up repro comment); fail if it is generic claim boilerplate ("+1", "claiming this", emoji pile) with no issue-specific anchor, or asserts a **completed rigorous reproduction** before a repro report exists. **Full package:** pass if the claim names **concrete issue behavior** (symptom, file, API, error class, or trigger construct) and does not contradict the repro; fail if it is assign-me/flattery boilerplate ("great project", "assign/reserve for me", guaranteed fix timelines) **without** that concrete anchor, or if it asserts reproduction that `symptom-matches-issue` would fail. | required |
| `analysis-not-overclaim` | Repro report analysis/conclusion plus claim comment if it restates certainty (see evidence guide: Honesty) | Pass unless the analysis or claim **asserts** the issue is confirmed/reproduced/"same failure as reported" while `trigger-faithful` or `symptom-matches-issue` would fail. Fail on confident wrong-target confirmation. Pass on honest cannot-reproduce or narrow wording tied to quoted artifacts. | required |
| `policy-disclosure` | Repo facts `contribution policy` line and both candidate comments (see evidence guide: Comms) | Pass if policy is **silent** on AI for issue comments, **or** allows assistive AI **without** requiring a disclosure line in comments, **or** the comments include the **disclosure the policy requires** (tool named, extent stated). Pass if policy only requires **human-authored** comments (no undisclosed AI slop) and both comments are **specific and human-voiced** (issue-anchored detail, not generic boilerplate). Fail only when policy **explicitly requires disclosing AI/tool usage** in issues or comments and **neither** comment discloses — eval packages are graded as if the student used AI assistance and must meet that disclosure bar when the repo demands it. | required |
| `issue-anchor-in-claim` | Candidate claim comment vs issue title/body | Pass if the claim references at least one **concrete symptom, file, endpoint, or error** from the issue (not only the issue number). Fail if the claim could apply to any open bug on the repo. | preferred |

## Verdict rule

**Accept** (ready to post) only if every **required** check passes.

**Reject** (hold) if any required check fails or is **unclear** (unclear counts as fail).

**Preferred** checks never change accept/reject; they only flag polish before posting.

In **claim-only** live grading, checks whose evidence is only in the repro report are graded `unclear` with evidence `not yet applicable: claim-only draft` and are **excluded** from the verdict; the verdict then uses only required checks that apply to the claim and policy.
